# CP 消息发布与订阅提醒规则

生效日期：2026-09-05。由项目所有者委托确定并实施。适用范围仅限 CP 的套餐、免费入口、临时权益与既有促销订阅；不包含社交平台发帖、购买服务、导入新联系人或扩大营销主题。

## 什么发布，什么发邮件

| 消息 | 网站 | 订阅邮件 |
| --- | --- | --- |
| 官方常规价格、套餐或政策调整 | 更新现行数据，保留变更记录 | 不发；不能为了发信把普通改价包装成折扣 |
| 已核验的免费额度、免费试用、限时折扣、临时加量 | 发布活动，说明资格与期限 | 按规则加入福利汇总 |
| 明确新增的一次 Reset、24 小时内结束或官方明确限量的权益 | 独立活动，注明北京时间 | 优先提醒，仍遵守频率上限 |
| 官方账号／身份已核验产品负责人的提前公告 | 标注“公告已核验，待正式到账” | 可以提前提醒，不承诺每个账户已到账 |
| 社区传言、普通员工单独表述、无法读取的原文 | 保留在 GitHub 待核验 Issue | 不发，不当作当前可用权益 |
| 同一活动到账说明、标题修正、转发或重复报道 | 更新原记录 | 不再发一封 |

永久降价更新价格表及最新消息，不等同于限时促销。免费试用必须写清时长、付费/绑卡条件、地区和结束规则；未披露的条件标注未知，不用估算补齐。

## 发送时间与频率

- 普通福利从每日 **北京时间 09:30** 开始汇总发送，无消息不发。GitHub 定时运行可能延迟，不承诺准点到达。
- Reset、官方明确限量、24 小时内截止的活动：网站部署成功后优先发；已排队的其他福利一起合并，避免同一批拆成多封。
- 每个滚动 24 小时最多 **1 封普通汇总 + 1 封优先提醒**，合计不超过 2 封。达到上限的消息留在网站并等待下一个发送窗口；到期后不补发。
- 每小时检查队列、发送回执和可用窗口；空队列不发邮件。每日扫描并不意味着每日有值得发送的新闻。
- 该时间仅针对读者福利邮件，不改变站长英国时间 09:30 的每日数据报告。

## 核验不是关键词命中

现有官网、免费模型目录与 X 扫描负责发现候选，**不会自动把抓取变化认定为事实**。维护者（包括获得本范围授权的 Agent）读取原始公告、核对身份、权益、适用人群、发布时间和截止时间，检查是否为同一事件，然后才提交正式数据及通知元数据。符合本规则的内容不再逐条请求站长批准；不确定则进入待核验队列。

必须区分三种时间：公告发布时间、权益生效时间、实际账户到账时间。所有对外时间用北京时间；不能因为预告时间已过，就把“待到账”改成“已到账”。同一政策每天自动发卡，不等于每天发布新活动。

直接官网证据须属于 `data/products.yml` 的相应厂商域名，且来源状态为 `verified`。官方社交公告须是 `data/social-watch.yml` 登记的 `official_account` 或有身份依据的 `product_lead` 原帖。社区、论坛及 GitHub 用户内容不能仅因域名属于某厂商而成为权威证据。新增可信账号必须先核验身份，再扩展允许列表。

读取不到 X 原帖、X API 未配置、抓取失败、只找到截图/转述时，不得伪造核验时间。保留来源链接和失败原因，报告缺口；不能声称所有渠道都已扫描。

## 活动的通知元数据

`data/offers.yml` 中原有 `verification` 控制网站事实标签；`subscriberNotice: early` 只控制预告文案，不再单独授予发信资格。要加入队列，必须另外提供：

```yaml
notification:
  eventId: vendor-benefit-2026-09-05
  announcedAt: "2026-09-05T08:00:00+08:00"
  reviewedAt: "2026-09-05T09:00:00+08:00"
  status: confirmed # confirmed / announced / review
  sourceId: vendor-original-announcement
  evidenceNote: "原公告明确公布权益、适用范围和时间；记录仍未知的到账条件。"
  limited: false # 仅当原公告明确限量时设为 true
```

- `confirmed` 要求 `verification: verified`；`announced` 要求 `subscriberNotice: early`；`review` 不发信。
- `sourceId` 必须属于此活动的 `sourceIds`，且与厂商一致。取证说明必须是实质摘要，不填写“已查”“待查”等空话。
- 一次真实权益对应一个稳定 `eventId`，转发、文案修正及后续到账沿用该 ID。只有原文明确新增一次独立权益才新建 ID。
- 公告/核验时间不能在未来，核验不能早于公告；超过 14 天的旧消息不进入新邮件。旧权益续期需新的官方公告与明确的独立事件，不靠修改日期重发。
- 邮件同时按事件 ID 和 X 状态 ID 去重，忽略 X/Twitter 域名大小写及分享参数。
- 普通字段修正不添加 `notification`。取消未发送通知可删除该字段；如果已创建待发草稿，须先安全核对草稿再清理队列。

## 上线与故障保护

工作流：`.github/workflows/promo-alert.yml`。测试通过、当前 `main` 在 Cloudflare 部署成功后才允许发信；人工触发默认 `dry_run: true`。

发送历史保存于 **`notification-state` 分支的 `notification-ledger.json`**，不使用容易被清理的缓存。第一次安装显式选择 `initialize: true`、`dry_run: false`，把当时所有活动纳入不补发基线，不会发送历史邮件。重复初始化或历史丢失时停止，禁止自动重建空记录。该分支只写公开活动 ID、批次、公开邮件内容和服务端回执，不写订阅者邮箱、访问令牌或邮件逐人明细。

发送分三步：先持久保存待发内容，创建 Resend 草稿并保存 ID，再保存发送意图并请求发送。网络不确定时读取同一草稿的状态；确认已发送/排队后记账。无法确认时停止并创建/更新 GitHub 故障 Issue，不能重新建一封再发。草稿内容过期或与新核验结果不一致也会停止。

Resend 的邮件幂等键文档只明确覆盖邮件接口，不能假定 Broadcasts 同样受保护。实现依据：[创建群发](https://resend.com/docs/api-reference/broadcasts/create-broadcast)、[查询群发](https://resend.com/docs/api-reference/broadcasts/get-broadcast)、[发送群发](https://resend.com/docs/api-reference/broadcasts/send-broadcast)、[幂等键范围](https://resend.com/docs/dashboard/emails/idempotency-keys)。

### 异常处理

1. 查看 GitHub 运行摘要、状态分支及 Resend 中对应的 `broadcastId`。只用该 ID 核对，不导出订阅名单。
2. 已接受/发送的批次：重跑会只做状态核对与记账，不再次请求发送。“已接受”不代表每位订阅者都收到。
3. 状态仍为 draft 且有发送意图：查 Resend 日志确认是否接受。未经明确排除已发送前，保留暂停状态。
4. 确认未发送且取消了草稿后，才能经审核清理 `pending`；保留原有 `completed`、`batches`、基线和 Git 历史。不要重置整个状态文件。
5. 不把测试消息发给真实订阅者。用单元测试与 `dry_run` 验证无新增邮件、去重和频率限制。

故障通过 GitHub 运行失败和单一 Issue 留痕；发现异常的维护 Agent 应通知站长。不要把 GitHub Issue 的产生描述为“已通知到每位用户”。
